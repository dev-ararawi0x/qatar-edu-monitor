Notification architecture

Persistence

notifications is user-owned, cascade-deleted with the user, type-checked, indexed for owner listing/unread lookups, and uniquely keyed by (user_id, idempotency_key) so repeated worker outcomes cannot duplicate rows.

Application boundary

RecordJobNotification creates completion/pause/failure messages. ListNotifications and MarkNotificationRead enforce actor ownership. Notification failure is logged as a warning and never writes back to the job.

Web and Worker

The Worker invokes the notification use case only after the job outcome is already settled. Web exposes GET /api/v1/notifications, POST /api/v1/notifications/:id/read, and the protected polling /notifications page.

Verification evidence

  • Application unit tests cover idempotent creation, owner-only listing, read marking, and cross-user non-disclosure.
  • A PostgreSQL integration test verifies idempotency uniqueness, owner scoping, and read persistence.
  • Migration 0006_notifications.sql was generated and applied to the local verification database.
  • Worker notification delivery is best-effort and isolated from job lifecycle transitions.
